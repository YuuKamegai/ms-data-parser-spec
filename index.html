01

全体像とアーキテクチャ

MS-DIAL は解析結果を圧縮 MessagePack と独自バイナリで書くため、GUI の外では読めず、チャットに貼るには大きすぎる。このサーバはそれらを読み、前処理・比較・PCA・同定の裏取り・定量の工程をサーバ側で回し、LLM には結論が埋もれない大きさの要約・TSV・PNG だけを返す。生の行列は LLM の文脈に載せない。

入口は 2 つで、どちらも MS-DIAL の解析フォルダで合流する。GUI で解析済みのフォルダを読む入口（list_data_files → load_dataset）と、生データから MS-DIAL Console を回してそのフォルダを作る入口（pipeline_*）は対等で、どちらから来てもその先は同じ 1 本の鎖（概観 → キュレーション → 定量 → 前処理 → 比較）を通る。pipeline は上流（Console の実行・出力の検証・受領）だけを受け持ち、統計は計算しない。入口の選び方は 3 章。

設計原則

文脈を守る

生の行列を返さない

JSON は json_payload() で空白なし、一覧は列名 1 回の TSV、float は丸める。全ツールに structured_output=False（付けないと同じ内容が 2 回送られる）。

図は画像で

座標より PNG

volcano の点列は実測 183,578 字 ≒ 数万トークン、サーバで描いた PNG は約 327 画像トークン。画像トークンは 幅×高さ/750 なので dpi は上げない。描画は dataset_plot(kind=…) の 1 本。

失敗の形

例外でなく封筒

前提状態が無いときは missing_state、利用者の判断が要るときは needs_input の JSON 封筒を返し、次に呼ぶツールを機械可読で伝える（4 章・13 章）。

状態の分離

データセットはハンドルごと

読み込んだものはすべて DatasetState としてハンドルの登録簿に入る。共有の無修飾スロットは作らない（別の読み込みが進行中の解析を無言で消すため）。閉じたハンドルの代わりに別のハンドルへ黙って落ちない。

推測しない

曖昧なら止める

複数候補のアラインメント・mzTab・LBM・極性の単位・メソッドファイルは、更新日時や辞書順で黙って選ばず、ALIGNMENT_AMBIGUOUS AMBIGUOUS_PRIMARY_MZTAB LBM_AMBIGUOUS や needs_input、候補の一覧で止めて選ばせる。

根拠の水準

確度を名乗らせない

MS/MS の「フラグ」と「実スペクトル」、MS1 注釈と MS/MS 証拠、gap-fill と実検出を全経路で区別する。比較の判定は changed / unchanged / inconclusive で、「有意でない」を「変わっていない」と読まない。

2.1 バイナリの解き方

MessagePack の Key 番号の正解表は docs/schema/*.md（MS-DIAL の C# クラスの [Key(N)] から上流 commit 45a531c 時点で抽出）。インデックス定数を変える前に必ずここを見る。推測で直さない。

.arf · arf/reader.py

LZ4 包みの MessagePack ストリーム

  1. トップレベルの msgpack オブジェクト（ExtType か [header, ExtType|bytes]）を順に読む。
  2. ブロック先頭の msgpack int が展開後サイズ。lz4.block.decompress(rest, size) で中身を得る。
  3. 中身はスポット「群」（行のリスト）。群の通し番号が MasterAlignmentID。
  4. unpacker は unicode_errors="ignore"（POS ファイルに壊れた UTF-8 がある）・strict_map_key=False・1 GiB バッファ。

行の Key: 0 FileID · 1 FileName · 2 MasterPeakID（負 = gap-fill）· 3 PeakID · 9 MS2RawSpectrumID · 10 MS2RawSpectrumID2CE（非空 = MS/MS 取得）· 15 ChromXsTop（RT）· 18 PeakHeightTop · 20 AreaAboveZero · 21 AreaAboveBaseline · 22 Mass · 37 PeakShape [noise, S/N]

.dcl · dcl/reader.py

固定長ブロックの独自形式

  1. ヘッダ 11 B: "DC" ＋ int32 版 ＋ bool 注釈 ＋ int32 件数。続いて件数 × int64 のシーク位置。
  2. レコードごと: Scan 60 B（+8 ScanID、+12 RawSpectrumID、+16 PrecursorMz f64、+24 IonMode i32、+28 RT f64）→ Quant 5×f64 → Scoring 5×f32（amp・purity・quality・S/N・noise）→ Counts 3×i32 → ピーク 20 B ずつ（mass f64・intensity f64・quality i32）。
  3. アラインメントの .dcl は dcl_index がスポット ID に対応する。索引だけを信じず、.arf2 の precursor m/z・RT と ±0.05 Da・±0.2 分で照らしてから使う。個別測定の .dcl は同名 .pai2 のピーク順に対応する設計。
.EIC.aef · eic/reader.py

magic CSS1 → offset 10 へ → int32 スポット数 → int64 ポインタ列。スポットごとに 4×f32（rt・ri・mass・drift）・i8 main_type・i32 試料数、試料ごとに i32 file_id・i32 点数・f32 top/left/right、続いて (f32 x, f32 強度) × 点数。描画とキュレーションは必要なスポットだけをポインタで直接読む。

2.2 同定の 2 つの出所

gap-fillmzTab-M の abundance_assay[N] は非ゼロでも実測か補間かを区別しない。実データ（60 試料 × 714 特徴）ではセルの 70.0% が gap-fill で、非ゼロを検出と数えると検出率を 3 倍以上に過大評価する。解析フォルダから読むと detected_mask は .arf の MasterPeakID から直接決まる。mzTab-M から読むときは、隣接 .arf が同一アラインメントだと数値で確かめられたときだけ（スポット数一致と全特徴の m/z 差 0.01 Da 以内）取り込む。
InChIKey解析フォルダでは .arf2 の InChIKey（無ければ代表の照合結果のもの）を使う。mzTab-M では database_identifier（InChIKey の正規表現に一致するとき）→ 研究室の MSP の表 → RDKit（InChI・SMILES から導出）の順。MS-DIAL は SML の inchi を常に null で書き、database_identifier は <db>:<name> 形式なので、RDKit で届くのは SMILES 経由だけ。

03

2 つの入口と 1 本の鎖

入口は 2 つあり、合流点は「MS-DIAL の解析フォルダ」。GUI で解析済みのフォルダを読む入口と、生データから MS-DIAL Console を回してそのフォルダを作る入口は対等で、どちらから来ても、その先は同じ 1 本の鎖を通る。サーバ共通指示（MCP_INSTRUCTIONS の ENTRY POINT / ASSAY KIND）はこの判定を LLM に教え、最初に呼ぶツールを絞らせる。

2 つの入口は対等LLM はまずフォルダに MS-DIAL を動かした形跡があるかを確かめる（list_data_files(directory)。directory は必須で、既定の探索先は無い。all_files=True で生データも見える）。.arf / .arf2 / .dcl / .EIC.aef・mzTab-M・完了した analysis-job.json・完了した pipeline の run のどれかがあれば、生データが同居していても下流へ進む（load_dataset）。MS-DIAL の再実行は利用者が明示したときだけ。形跡が無いときは、MS-DIAL Console を回してよいか（1 極性あたり数十分かかり、生データの側に run フォルダを書く）を利用者に尋ね、同意するまで何も起動しない。同意したら pipeline_run（起動前に解決結果を見たいなら pipeline_plan、メソッドファイルを選ぶ・作るなら console_method_candidates / console_method_template）。Console の入口が作るのは極性ごとの解析フォルダで、pipeline_status が completed / partial を返したら load_dataset(pipeline_path=…, polarity=…) で GUI の入口と同じ鎖へ合流する（9 章）。
アッセイ種別脂質（lipid）か一般代謝物（metabolite）かはファイル形式からは分からない（MS-DIAL は同じ .arf / mzTab-M に両方を書く）。確定するまで脂質の略記文法もクラスの知識も当てない。記録には読み込み済みのデータセットが要るので、確定は load_dataset の後: LLM は群・極性・化合物クラスから目的と生物学的文脈の候補を 1〜2 個、根拠つきで示し、利用者が確かめたものだけを record_objective(assay_kind=…) で記録する。metabolite では GOSLIN / LIPID MAPS の正規化と脂質の検査は当てはまらず、同定は候補の集合（付加体・異性体・順位）で語る。
並行の再解析複数のエージェントが同じサーバを使う再解析では、直近のデータセットを当てにしない（load_dataset は開いたハンドルを必ず直近にし、dataset_handle を省いた呼び出しはそれに効くので、互いに直近を切り替えてしまう）。load_dataset が返した dataset_handle を dataset_*・library_*・curation_*・再解析のツールに渡す（開いているハンドルは dataset_list / dataset_close で管理する）。判定に使う数字は spec で呼ぶツール（dataset_analysis_run / dataset_claim_evidence / library_msms_qualify）から取り、結果を読む前に dataset_alignment_qc で割れたスポットを探す（MCP_INSTRUCTIONS の PARALLEL REANALYSIS。5 章）。

3.1 鎖の中の枝：アラインメントのキュレーション

MS-DIAL の GUI で 1 件ずつ見ていた注釈の確認（EIC・対向プロット・Δm/z・ΔRT・RT–m/z の線形性）を、一覧と機械判別で短くする枝。鎖の中では最初の概観の後・定量の前に置く人の判断の止まり場所だが、行列そのものは変えないので、load_dataset の後ならいつでも入れる。前提は 2 本で、どちらも missing_state で止まる：データセットが .arf2 を持つこと（解析フォルダから読んだもの。mzTab-M だけなら理由つきのエラー）と、そのデータセットのライブラリがあること（load_dataset の既定 library="auto" は、データセットが同定に使ったライブラリの記憶を sha256 で確かめてから開く。開けなかったとき（library_note に理由）だけ library_load(file_path=…)。アラインメントと同じフォルダの *_Loaded.msp2.dbs を推奨）。

  1. curation_review — 一覧と機械判別

    注釈付きスポット（既定は全部、ontology でクラス、name_contains で名前）の証拠を集めて判定し（8 章）、ビューア HTML を書く。LLM に返すのは suspect 以上とフラグ済みの TSV・件数・クラス別の傾向要約・html_path だけで、EIC 系列とスペクトルは返さない。

  2. 利用者がビューアで確かめる

    html_path をブラウザで開く。likely_wrong は赤の破線枠で「間違い」が初期選択、メモ欄には判定根拠が入っている。クラスの選択肢の「<クラス> › likely_wrong」で絞れる。正しいと確かめたものは Confirmed にチェックする。直したら Submit を押すと、ビューアが手元の受け口（サーバと同じマシンの loopback）へ直接送って、記録と _tags.xml の反映まで済ませる（LLM を介さない。Finish か 30 分の無通信で閉じる）。受け口が無いとき（時間切れ・サーバ再起動）だけ「Copy submission text」でチャットに貼る。MCP Apps で会話の中に出すビューアもある（リソース ui://ms-data-parser/curation-viewer。データは curation_view_data が渡し、LLM は呼ばない）。

  3. 記録と MS-DIAL への反映（ビューアの Submit か curation_submit）

    どちらも同じ検証・記録。flags.jsonl に追記し（正本）、アラインメントの _tags.xml の Confirmed と Misannotation を付け外しする（confirmed → Confirmed を付け Misannotation を外す、wrong → Confirmed を外し Misannotation を付ける、suspect → Confirmed を外す、取消 → 両方外す）。書いた後、同じ .arf2 を開いているハンドルすべてがフラグを読み直す。

  4. curation_suggest — 間違いと未注釈への候補付け

    任意の続き。wrong のスポット（既定は元レビューの likely_wrong も）と未注釈スポットに、MS-DIAL の下位候補・閾値を緩めた再検索・別スポットのイオン（同位体・付加体・インソース断片）としての説明を並べ、候補付けビューアを書く（8 章）。利用者が選んで送信する（受け口が無ければ curation_submit に貼る）と、assign（この名前で記録）か redundant（別スポットのイオンなので消す）として記録する。_tags.xml は変えない。

  5. 書き出し・選別・図に効く

    dataset_export_differential / dataset_export_evidence_bundle は既定（apply_curation=True）で wrong と redundant のスポットを外し、assign のスポットは同定を記録した値に置き換えて（name_source / inchikey_source = curation）、メタ行 # curation = … で宣言する（10 章）。dataset_select_features は選別の最初の段でキュレーションを当て、dataset_plot の group_intensity / species / species_pca も apply_curation を持つ。curation_flags で有効な判断を一覧でき、dataset_overview で概観を出し直せる。

フラグの意味レビューで記録するのは「間違い」（wrong）・「疑わしい」（suspect）・「確認済み」（confirmed）。無印は「間違っていない」の意で、何も記録しない。候補付けで記録するのは assign（記録名・InChIKey を持つ）と redundant（相手スポットを持つ）。フラグは .arf2 の sha256 と MasterAlignmentID の組で持つので、MS-DIAL を再実行してアラインメントが変わると古いフラグは当たらなくなる（件数は warnings で知らせる）。

5pipeline（生データフォルダ起点のもう一方の入口）

GUI で解析済みのフォルダを読む入口と対等な、もう一方の入口。生データフォルダ 1 つから、raw を run の中（<run>/<極性>/input/）へ配置し、極性ごとに MS-DIAL Console を回し、できた解析フォルダを mzTab-M と照合して受領（results/receipt.json）を書くまでを 1 本の永続 run（pipeline-run.json）として進める。統計は計算しない——続きは load_dataset(pipeline_path=…, polarity=…) で同じ鎖へ合流する。LLM はフォルダに MS-DIAL の形跡が無く、利用者が Console を回すことに同意したときだけ呼ぶ。

前処理・比較・PCA は 1 つの統計エンジン（metabolomix/analysis/stats/。MCP にもセッションにも依存しない純計算）が持つ。入口は dataset_preprocess だが、dataset_compare・dataset_pca・pathway_project・dataset_overview も matrix_id を省けば同じ前処理を既定の設定で回し、dataset_analysis_run（analysis-spec.v2）も同じ関数を通る。読み込んだだけのデータセットには何も適用されない。出力は個体 × 特徴の log2 行列（NaN = 欠測）で、検定のための補完はしない。

  • drift_mode="on" で条件を満たさなければ PREPROCESS_PRECONDITION。auto で、内部標準などで換算済み（quant_state.normalized）のデータに QC があるときは既定を決めずに尋ねる（6.4）。

  • 未実施の理由: disabled（None 指定）/ no_blank / no_detected_mask / too_few_qc（QC 2 本未満）/ too_few_samples（D-ratio で生体試料 2 本未満）。

同定と MS/MS 照合

目的は「付いている名前は本当か」を、人が数値と図の両方で判断できるようにすること。同定はデータセットを読んだ時点で特徴ごとに 1 つ付き、そのあとを実スペクトル（.dcl）・参照ライブラリとの照合・主張ごとの証拠の束・アラインメントのキュレーションの 4 つの道具で確かめる。名前の標準化・MSI レベルの推定・スペクトル照合はすべてオフラインで、pygoslin（同梱）と同梱 TSV と参照ライブラリだけを使う。

8.1 同定を確かめる道具の地図

読み込み時に付く同定

あわせて .arf2 の名前を GOSLIN で正規化し、feature_metadata["identity"] に normalized・RefMet 名・LIPID MAPS カテゴリ・msi_level を入れる（dataset_feature_search の行にも出る）。.arf2 は精密質量誤差を持たないので質量の帯は UNKNOWN で評価され、この経路の msi_level は 3（クラスが分かる）か 4 にしかならない。mzTab-M 経路では常に空欄（「この経路では取得していない」）。

8.3 スペクトル照合（MS-DIAL MsScanMatching.cs の忠実移植）

目的は MS-DIAL との数値の一致で、実装の改善ではない。上流の「変な点」（未使用の中間値、両枝が同一の分岐、打ち消える ×999、隣接窓への二重計上を許すカーソル走査、Li et al. 2021 の低エントロピー重みの不在）は意図的にそのまま写してある。スコアの式は analysis/spectral_match.py にあり、許容幅の解決・候補の検索・並べ替えは library/matching.py 1 か所で、library_match_feature・library_msms_qualify・dataset_claim_evidence が共有する（キュレーションはスコアの式を直に使う）。

窓の合算焦点 m/z ごとに [m − b, m + b) の強度和、b = ms2_tol（既定 0.025 Da）。各系列を自身の最大値で割って Im,k・Ir,k
weightedS² = ( Σ √(Im,kIr,k) · mzk )²( Σ Im,k·mzk )( Σ Ir,k·mzk ) × penalty　（Im ≥ 0.01 の窓だけ）
penalty参照側で相対強度 > 0.1 の窓が 1 → 0.75、2 → 0.88、3 → 0.94、4 → 0.97、それ以外 1.0
reverse同じ式を参照ピークの範囲だけで、0.01 の足切りを参照側に掛ける
simpleS² = ( Σ √(ImIr) )² / ( ΣIm · ΣIr )　m/z 重み・ペナルティなし
matched peakspercentage = 一致窓数 / 参照ヒット窓数（参照和 ≥ 最大参照ピーク × 0.01）、count = 一致窓数
entropysim = 1 − ( 2·HAB − HA − HB ) / 2　（log2 の Shannon エントロピー、総強度で正規化、合成スペクトルは 0.5 倍）
返す値3 つの dot product は √ を取った値（mzTab の id_confidence_measure[4..6] と同じ土俵）
ガウス類似度g(a, r, tol) = exp( −½ ((a − r)/tol)² )　値が欠けるか ≤ 0 なら −1
質量許容の補正mass ≤ 500 ならそのまま、超えれば ppm = |round(tol/500 × 10⁶, 4)|、tol′ = ppm × mass / 10⁶
total_score= [rt_similarity（use_rt のとき）] + mass_similarity + (weighted + simple + reverse)/3（weighted > 0 のとき）+ matched_peaks_percentage　正規化しない和で 1 を超える。RT 項を足したかは戻り値の scoring.use_rt（.dbs の IsUseTimeForAnnotationScoring 次第。.msp は常に false）
−1 と 0−1 は「比較していない」（どちらかのスペクトルが空）、0 は「合わなかった」。混同すると「照合していない」が「合わなかった」に化ける。mzTab の dot product 3 列は上流で −1 を 0 にクランプしてから √ を取るので、比較不能はそこでは 0 として出る。
窓の分離ライブラリ候補の検索窓（mz_tol / rt_tol、明示 > .dbs の search_params > 既定 0.01 / 0.2）と、.dcl から測定スペクトルを引く窓（常に 0.01 Da / 0.2 分）は別物。.dbs の RtTolerance 既定 100.0 を .dcl 側に流すと、m/z が近い別ピークのスペクトルを黙って拾う。

照合の対象。library_match_feature は precursor_mz か spot_id のどちらか一方を取る。spot_id（MasterAlignmentID ＝ mzTab-M の SMF_ID）なら precursor m/z・RT・極性を .arf2 から取り、測定スペクトルはアラインメント .dcl のそのスポットの代表 MS/MS を使う（m/z で探さないので同じ m/z の別スポットを拾わない）。.arf2 と ±0.05 Da・±0.2 分で合わなければ照合せず dcl_precursor_mismatch。並び順は total_score だが、上流の順位付けタプル全体は再現していないので化学的にありえない候補が上位に残ることがある——1 位は library_plot_mirror の対向プロットで確かめる。detail=true で inchikey と前駆体を除いた一致の本数 fragment_matches_excl_precursor の列、測定スペクトル、候補ごとの一致ピークが足される。

8.4 アラインメントのキュレーション（機械判別）

curation_review はスポットごとに 6 系統の帯（PASS / BORDERLINE / FAIL / UNKNOWN）と理由コードを出し、総合判定 verdict にまとめる。画像ではなく数値に対して判定する。MS-DIAL 自身が同定時に出した判定（MsScanMatchResult のフラグ）を主にし、こちらでの再計算は食い違いの検出にだけ使う。UNKNOWN（MS/MS 未取得・参照 RT なし）は不一致に数えない。対象のデータセットは dataset_handle（省けば直近）で、.arf2・.dcl・.EIC.aef・.arf はそのデータセットが覚えた場所を使い、参照はそのデータセットのライブラリ（無ければ missing_state で library_load を促す）。1 回の上限は 3000 スポット。

系統見るもの基準
msmsMS-DIAL の is_reference_matched・脂質規則フラグ、.dcl の実スペクトルでの再照合参照一致なら PASS、MS/MS はあるのに不一致なら FAIL（low_score）、MS/MS なしは UNKNOWN
mz代表試料の m/z − 参照 precursor（引けなければ組成式の理論値）Δppm 5 / 10、|Δm/z| ≥ 10 mDa、MS-DIAL の precursor 判定、アダクトの電荷と測定極性

okそれ以外—

判定を動かさない情報コードもある: msms_absent · reference_not_found · rescore_discrepancy（こちらの再照合が MS-DIAL の値と 0.1 以上ずれた）· adduct_differs_from_reference · manually_modified · class_rules_not_run（脂質クラス規則が評価されていない＝未検証であって誤りではない）· rt_not_used_by_annotation（MS-DIAL がこの照合で RT を絞り込みにも採点にも使っていない。LBM の参照 RT は別グラジエントの予測値でありうるので、rt 系統を UNKNOWN にして drt_out / drt_borderline を立てない）· chains_unsupported（鎖レベルの名前なのに is_lipid_chains_match=False。MS-DIAL は照合に失敗しても参照名から | 付きの名前を作るので、| 名は鎖組成の証拠ではない）ほか。

脂質規則は脂質データでだけ読むMS-DIAL の脂質規則フラグ（IsLipidClassMatch / IsLipidChainsMatch / IsOtherLipidMatch）は Lipidomics 採点器でしか立たず、他の採点器では全部 false になる。そのまま読むと low score が全件「規則で棄却」に化けるので、対象スポットに規則フラグが 1 件でも true のときだけ 3 コードを使い、無ければ warnings で知らせる。
実測kidney（マウス腎、neg / pos、注釈 1468 / 2196 件）で likely_wrong は 424 / 563 件、うち class_rule_rejected が 370 / 404、dmz_out が 139 / 232。MS-DIAL の代表候補の再現は全件一致、参照の解決は 100%、1 回のレビューは約 5〜16 秒。

戻り値は suspect 以上とフラグ済みのスポットだけの TSV（判定の重い順の先頭 max_rows 行、既定 100。総数は n_table_rows_total）・判定の件数・クラス別の傾向要約・html_path・submit。全件は HTML ビューアにだけ入る。EIC の系列とスペクトルは返さない。ビューアは MCP Apps のリソース ui://ms-data-parser/curation-viewer としても配信され、その証拠は curation_view_data（ビューア専用。LLM は呼ばない）が渡す。

候補付け（curation_suggest）

間違いになったスポット（wrong フラグ、既定では元レビューの likely_wrong も）と未注釈スポットに、出所の違う 2 種類の説明を並べる。物差しが違うので 1 本の順位には混ぜない。先に library_load と curation_review が要る。

種類出所並べ方と制約
候補（①②）① MS-DIAL が保存した下位候補、② 閾値を緩めた再検索（スコアの足切りなし）ハードで削る: polarity_mismatch · dmz_out（|Δm/z| ≥ 10 mDa）。ソフトで順位を下げる: adduct_atypical · trend_outlier · no_matched_peaks · msms_absent。並び順は（ソフト理由の数 昇順、total_score 降順）で上位 top_n 件。total_score の -1 は「比較していない」で、一致度ゼロではない
イオン関係（④）注釈付きの別スポット Y の同位体（isotope_M+1/M+2）・別アダクト・インソース断片（-H2O ほか）、または MS-DIAL の found_in_upper_msms リンク|ΔRT| ≤ rt_window かつ Δm/z ≤ relation_mz_tol。裏付け（MS-DIAL のリンクか、試料間の強度相関 r ≥ relation_min_r）が無ければ no_support。強い説明は裏付けがあって found_in_upper_msms 系か同位体比が合うものだけで、アダクトの組・断片は Δm/z が合うだけでは強い説明にしない
記録と反映ユーザーはビューアで候補を選んで「送信」する（受け口が無ければ送信用テキストを貼る）。assign は選んだ候補の名前（既定は和組成。MS-DIAL の脂質規則を評価していないので鎖組成は保証しない）・クラス・InChIKey を、redundant は相手スポットを記録する。dataset_export_differential は既定（apply_curation=true）で wrong と redundant を外し、assign の同定で置き換える（name_source / inchikey_source = curation。未注釈だったスポットも新しく現れる）。実測（kidney neg）: 未注釈スポットの MatchResults は Source=Unknown のダミー 1 件だけで、MS-DIAL は足切り以下の候補を保存しない——②の再検索が要るのはこのため。

ビューアとフラグの流れ

  • 判定根拠のメモ。likely_wrong と suspect のカードは、メモ欄の既定値が判定根拠の文になる（例 Auto: m/z — Δm/z 12.4 mDa (≥10 mDa) / MS2 — no match to the reference (low score)。2026-10-09 に英語化。それより前の記録は日本語のまま）。
  • MS1 同位体と傾向カード。MS1 パネルは .arf2 の IsotopicPeaks（代表試料の M, M+1, M+2）の「実測 % (絶対強度) / 理論 %」を出す（理論は組成式＋アダクトの畳み込み。判定には使わない）。RT–m/z の傾向カードは Plotly で描く。
  • Confirmed。各カードの Confirmed チェックは判断 confirmed（注釈が正しいと確かめた）で、Suspect / Wrong と排他。初期状態は記録の confirmed か、レビュー作成時の _tags.xml の Confirmed（GUI で付けたものも）。確かめたスポットには likely_wrong の初期選択・dataset_plot（group_intensity / species / species_pca）の exclude_auto_likely_wrong・curation_suggest の likely_wrong 対象を当てない。
  • 「間違い」の初期選択。likely_wrong・理由 low_score・情報 msms_absent のスポットは開いた時点で Wrong が選ばれた未送信の変更になる（送信すると _tags.xml の Misannotation にも反映されるので、残したいものは Correct に戻す）。記録済みのフラグがあるもの・人が取り消したもの（flag_cleared）には掛けない。「なし」に戻して送れば取消として記録され、次のレビューで掛け直さない。
  • 枠。自動判別の likely_wrong は赤の破線、記録されて（または人が選び直して）「間違い」になると実線。人の「疑わしい」は橙の実線。
  • 対向プロット。ピークの m/z ラベルは library_plot_mirror と同じ規則（強度降順の貪欲法、縦横とも重なるものを飛ばす、片側 25 本まで、実測と参照は独立）。縦軸は各側の最大値を 100 とした相対強度で 0 / 50 / 100 の目盛り。
  • 参照の引き当て。照合結果の注釈器 ID からライブラリを引くのに、.dbs の Storage にある「注釈器 Key → ライブラリ名」の対応を使う（GUI の命名規則から推測しない）。MS-DIAL Console のアラインメント（注釈器 ID が LBM のパス等）でも参照スペクトルを引け、対向プロットと再採点が出る。
  • 記録の置き場所と、開いているデータセットへの反映。フラグは .arf2 の隣の curation/flags.jsonl に追記し、.arf2 の sha256 を添える（同じ名前で sha256 が違う以前の版に付いたフラグは当てず、件数を warnings で知らせる）。curation_submit は書いた後、同じ .arf2 を開いているハンドルすべての判断を読み直す（戻り値の open_handles）ので、書き出しの apply_curation は新しい判断をすぐ使う。有効な判断は curation_flags（spot_id・flag・name・of・note・source・ts）と dataset_feature_search の curation_flag 列で読める。
  • MS-DIAL への書き戻し。ビューアの Submit と curation_submit はアラインメントの <stem>_tags.xml を上流 AlignmentResultContainer.Save と同じ形（<Peak Id="MasterAlignmentID"><Tag>3</Tag></Peak>、UTF-8 BOM・CRLF）で書く（控えは curation/tags-backup/）。実物の写しで付与 → 除去の往復がバイト一致することを確かめてある。MS-DIAL でプロジェクトを開いたままだと GUI の保存で上書きされる。
共有の注意レビューの HTML / JSON は、読み込んだ参照ライブラリのスペクトル（対向プロットの参照側）をそのまま埋め込む。研究室のライブラリを読んで作ったレビューは、ライブラリ本体と同じく研究室の外へ出さない。

9.6 再開・取消・旧形式の run

pipeline_resume(pipeline_path, updates, request_id, rerun_upstream=False) の updates で変えられるのは試料の対応表だけ（1 極性の run はトップの sample_manifest、2 極性は units: {<極性>: {"sample_manifest": …}}）で、変えると受領だけを書き直す。上流の条件（メソッド・ライブラリ・極性…）を変えるなら新しい run（NEW_PIPELINE_REQUIRED）。prepare_resume は戻す工程を決めて保存するだけで、自分では worker を起動しない（planned に戻したときだけ resume_pipeline が起動する）。判断の順:

  1. updates を検証して統合する

    下流のキーは PIPELINE_DOWNSTREAM_REMOVED、上流の条件の変更は NEW_PIPELINE_REQUIRED。request_id 付きの再送が直前と同じなら、新しい revision を作らず直前の結果を返す。

  2. 見張られていない Console が生きていれば止める

    EXECUTION_UNRESOLVED（待ってから呼び直す）。

  3. 上流のやり直しは明示を求める

    Console の状態が分からない単位がある、または進められる単位が 1 つも無いのに rerun_upstream が無ければ UPSTREAM_RERUN_REQUIRED。Console の自動再試行はしない。失敗した単位があっても他を進められるなら止めず、失敗した単位はそのまま（not_retried_units）。worker が生きていて Console が走っている単位は、やり直しの対象にも理由にも数えない（held_units）。

  4. やり直す単位の 3 工程を pending へ戻す

    rerun_upstream=True は upstream が成功していない単位だけを新しい attempt でやり直す。成功した単位の Console は再起動しない。

  5. 戻さない単位の固定済み入力を再検証する

    元の raw・メソッド・LBM・MSP・実行体が変わっていれば INPUT_CHANGED、配置済みのコピーや注釈器の表が変わっていれば STAGED_INPUT_MISMATCH。

  6. 受領を戻す

    試料の対応表の更新・同じパスのシートの書き直し（内容 hash で検出）は受領だけを戻す（アライメントの参照ファイルは計画の時点で固定済み）。どれかの工程を戻したら受領も戻す。planned に戻したら取消フラグを取り下げる。受付で needs_input に止まった run は、起動する前に単位ごとのシートの事前検査をやり直し、直っていなければ起動しない。

pipeline_cancel が保存するのは協調的な取消フラグ（小さな JSON）だけで、プロセスを直接終了させず、raw データは削除しない。Console の停止は supervise の取消フラグの監視に、工程の停止は engine の工程の境目の確認に委ねる。受理と停止の確定（cancelled）は別で、後者は pipeline_status で確かめる。

旧形式の run構成見直しの前の run（pipeline-run.v1）は読むだけ。pipeline_status は legacy: true と注意 1 行を付けて読め、load_dataset(pipeline_path=…) はデータセットとして開く（解決済みの試料の対応表も読む）。pipeline_resume / pipeline_cancel は PIPELINE_RUN_LEGACY で断る（読むなら load_dataset、Console をやり直すなら新しい pipeline_run）。run の中の古い差次的結果は引き継がない——統計は対話の鎖（dataset_preprocess / dataset_compare / dataset_pca）で計算し直す。

A. GUI で解析済みのフォルダを開き、2 群を比べる

「このフォルダを見て。ILG 6h と control 6h で何が変わった？」
list_data_files→load_dataset→record_objective→dataset_status→dataset_exclude→dataset_preprocess→dataset_compare→dataset_plot→dataset_export_differential→write_report
  1. list_data_files で MS-DIAL の出力があることを確かめ、load_dataset(directory=…) が最新バッチの PeakProperties.arf を選んで開く。戻り値の overview は品質 → 全体 → クラス → 分子種の粗い地図で、LLM は品質の段を先に示す（poor なら差より先にそう言う）。2 群の向きはまだ仮（試料の表で先に出た群が基準）。
  2. LLM は群・極性・クラスから目的の候補を 1〜2 個、根拠つきで示し、利用者の確認を得てから record_objective(assay_kind="lipid", …) で記録する。
  3. dataset_status(view="samples", query="ILG_6h,control_6h") で試料を確かめる（Class ID に時点が無くても、名前の因子トークンで切り出せる）。外れた失敗注入があれば dataset_exclude(samples=[…], reason=…) で可逆に外す（残すと QC RSD の足切りでほぼ全特徴が落ちる）。
  4. dataset_preprocess(group_levels=["control_6h", "ILG_6h"]) が matrix_id を返し、dataset_compare(reference_group="control_6h", test_group="ILG_6h", matrix_id=…) で向きを決めて比べる。判定は changed / unchanged / inconclusive の 3 値で、「有意でない」は「変わっていない」ではない。交絡・小 n・正規化の注意はレポートの注意点に写す。
  5. 画面で見るなら dataset_plot(kind="volcano")（PNG が直接返る）、下流のパスウェイ解析へ渡すなら dataset_export_differential(output_path)（契約 TSV）。結論は write_report で解析フォルダの reports/ に残す。

B. 生データから解析フォルダを作り、同じ鎖へ合流する

「raw/pos と raw/neg の生データを解析して、ILG と control を比べて」
list_data_files→pipeline_plan→pipeline_run→pipeline_status→pipeline_resume→pipeline_status→load_dataset(pipeline_path, polarity)→dataset_compare
  1. list_data_files(directory, all_files=True) で MS-DIAL の形跡が無く計測データだけだと確かめ、MS-DIAL Console を回してよいか（1 極性あたり数十分かかり、生データの側に runs/ を書く）を利用者に尋ねる。同意するまで何も起動しない。
  2. 解決結果を先に見せるなら pipeline_plan(dataset_root, request={"units": [{"polarity": "positive", "raw_dir": "raw/pos"}, {"polarity": "negative", "raw_dir": "raw/neg"}]})。メソッドの候補が割れていれば console_method_candidates で選び、その極性で GUI 実行が一度も無ければ console_method_template で別極性から作る。
  3. 同意を得て、同じ要求で pipeline_run。数秒で pipeline_path が返り、worker が 1 極性ずつ Console を回す。pipeline_status で進捗を見る（呼ばなくても worker は最後まで進める）。
  4. 実験情報シートが壊れていれば、Console を起動せず needs_input で止まる。直すのはシートだけで、pipeline_resume(updates={"units": {"negative": {"sample_manifest": …}}})。片方の極性の Console が失敗しても、もう片方は進んで run は partial になる。失敗した極性をやり直すのは、利用者の同意を得て rerun_upstream=True を渡したときだけ（自動再試行はしない）。
  5. completed / partial になったら、受領の next どおり load_dataset(pipeline_path=…, polarity="negative") と polarity="positive"（ハンドルが 2 つ）。pipeline は統計を計算しないので、比較の群と向きはここから A と同じ鎖で dataset_compare が決める。

C. 実験情報の誤記を直して計算し直す

「QC_05 は実はバッチ 2 だった。群も 1 つ入れ違っている」

  2. 試料の表が変われば（group だけの変更でも）、登録した行列・比較・PCA の結果は古くなる（changed_fields で確かめる）。dataset_preprocess からやり直す。
  3. 古い結果を書き出そう・描こうとすると STALE_ANALYSIS_RESULT で止まり、取り違えが起きない。最初の概観も dataset_overview で出し直す。
  4. pipeline の run の受領に載る対応表も直すなら pipeline_resume(updates={"sample_manifest": …})。書き直すのは受領だけで、Console は再実行されない（同じパスのシートの書き直しも内容 hash で検出される）。

F. 注釈を一覧で確かめ、誤同定を MS-DIAL に返す

H. 論文の解析を並行のエージェントで再現する

「この論文の方法どおりに計算し直して、主張が再現するか数字で確かめて」
load_dataset→dataset_alignment_qc→dataset_analysis_run→dataset_claim_evidence→library_msms_qualify→dataset_novel_candidates→dataset_close
  1. 各エージェントは load_dataset が返した dataset_handle をすべての呼び出しに渡す（直近を当てにしない）。別のハンドルへの呼び出しは並行に、同じハンドルへの呼び出しは 1 本ずつ進む。
  2. 結果を読む前に dataset_alignment_qc で、1 つの物質が 2 つのスポットに割れた組（例: 最初の注入の RT が流れた）を探す。まとめてよい組（mergeable）は統計の側が試料ごとに大きい方の値で 1 列にする。
  3. 論文の方法を analysis-spec.v2 に写して dataset_analysis_run(spec)。前処理を 1 回回して compare / composition / pca を実行し、rule_hash と判定の件数を返す。spec だけで再現する自己完結の実行で、dataset_exclude の除外は読まない（除外は spec に書く）。
  4. 主張ごとに dataset_claim_evidence(spec)（既定の特徴・許容幅を広げた走査・MS/MS の照合と合否・関係を 1 つの JSON に）と library_msms_qualify（msms-rules.v1 の合否）。返すのは数字と rule_hash で、「再現した」という結論は返さない。
  5. 新しい知見の候補の一覧は dataset_novel_candidates。終わったら dataset_close でハンドルを手放す。

エラー契約とコード一覧

失敗は例外ではなく、本文の JSON 封筒で返す（SDK の isError の経路は structuredContent を落とし、-> str のツールは失敗時だけ別の型を返せないため）。封筒は 3 種類: 前提の状態が無い missing_state、確定した誤りの error.code、利用者に尋ねる needs_input（エラーではない）。封筒・戻り値には研究室の参照ライブラリの置き場所を載せない（ファイル名だけ）。

missing_state（前提の状態が無い）
{"error":{"code":"missing_state",
  "state":"stat_matrix",
  "required_tools":["dataset_preprocess"],
  "message":"行列 'mx_…' がありません（…古くなりました）。dataset_preprocess を実行し直して…"}}

state は不透明な文字列として扱う。required_tools は OR の代替候補で、サーバは実際の生成元を漏れなく挙げる義務がある。クライアントは候補のうち本セッションで成功した直近の呼び出しを記録済みの引数のまま再実行して状態を戻せる。3 つの欄はどれも欠かせない（欠けた封筒は作る側で ValueError）。

needs_input（尋ねてから呼び直す。エラーではない）
{"needs_input":{"field":"preprocess.drift.mode",
  "reason":"内部標準で換算済みの値に QC があります…",
  "options":[{"value":"on","label":"…"},{"value":"off",…}],
  "argument":"drift_mode",
  "retry_tools":["dataset_preprocess"]}}

error キーを持たない。クライアントは答えを推測せず、options を利用者に見せて選んでもらい、value を argument に入れて retry_tools のどれかを呼び直す。spec で答える dataset_analysis_run の経路は argument を持たず、答えを spec の field に入れる。

13.2 error.code の封筒

確定した誤り（DomainError から作る封筒）
{"error":{"code":"DATASET_HANDLE_LIMIT",
  "message":"開いているハンドルが上限（8）に達しています。使い終えたハンドルを dataset_close で閉じてください…",
  "details":{"open_handles":["dh_…",…],"max_handles":8}}}

details は任意（統計エンジンのツールは長い一覧を切り詰めて載せる）。missing_state と違い、別のツールを先に呼んでも直らない——引数・入力・設定を直して呼び直す。Console のメソッドや pipeline の封筒は、自分の直し方を required_tools で指すことがある（例: 土台の候補が複数の METHOD_FILE_CHOICE_REQUIRED は console_method_template）。実行体が未設定のときは human_action_required: true と、設定ファイルの場所・キー・コピーできる手順を details に載せる（設定ファイルの編集は MCP クライアントにはできないため）。

形の違う例外が 2 つある。library_load とキュレーションのツール（curation_*）、dcl_* の一部は {"status":"error","code"?,"message",…} で返す。定量のツールの status:"needs_input"（内部標準の曖昧・試料の食い違い・採用表の未設定）は上の封筒ではなく、各ツールの戻り値の形（how_to_answer に次の呼び方）。

14.2 戻り値を小さく保つ決まり

JSON

json_payload()（separators=(",",":")、ensure_ascii=False）。indent=2 は書かない（実測で戻り値の 15〜57% が空白だった）。

表

行が並ぶ一覧は format_spots_as_table() の TSV（列名 1 回、float は小数 4 桁まで、区切りを含むセルは引用符）。

数値

float は丸めてから返す（round_floats() 既定 6 桁）。既定 repr は 17 桁出る。

二重送信を防ぐ

全ツールに structured_output=False。付けないと outputSchema が導出され、同じ内容が content と structuredContent の両方で送られる。

中間データ

行列は ds.stat_matrices、比較・PCA の結果は ds.results、図の記録は ds.figures に持ち、戻り値は要約と ID（matrix_id / result_id）だけ。図の保存・書き出しはそこから読む。行の多い表は output_path へ書かせる。

画像

図はサーバで描いて PNG で返す（volcano の点列 約 18 万字に対し、画像は数百画像トークン）。dpi 100 固定。画像トークン ≈ 幅 × 高さ / 750 なので dpi を上げると二乗で増える。

14.3 既知の限界

  • 版依存。バイナリリーダは MS-DIAL の内部クラス配置に従う。クラスを変える MS-DIAL のリリースでは docs/schema/ の Key 番号の再確認が要る。
  • 大きな .arf。読むときに解析で使う Key 以外は捨てるが、伸長後の大きさの見積もりが空きメモリを超えるときは読み始めずに、読む途中でメモリが尽きたときも ARF_TOO_LARGE で止める（見積もりと対処を details に）。
  • mzTab-M だけでは検出と gap-fill を区別できないことがある。解析フォルダから読んだデータセットは .arf の印（detected_mask）を常に持つ。mzTab-M の経路は隣の .arf が同じアラインメントだと数値で確かめられたときだけ取り込み、detection.available が false の間は検出率・欠測率を主張しない（実データでセルの 70% が gap-fill だった例がある）。
  • 「有意でない」は「変わっていない」ではない。判定は changed / unchanged / inconclusive で、unchanged は 95% CI が同等の範囲に収まるときだけ。n が小さい・ばらつきが大きいときの大半は inconclusive。片方の群で実際の検出が半数に満たない特徴も、量の差は判定しない。
  • 補完は検定に使わない。PCA など完全な行列が要る計算にだけ補完し、使ったことを結果に書く。
  • ドリフト補正は条件つき。QC の LOESS をバッチごとに当て、バッチ間の水準を QC の中央値でそろえる。QC が無い・注入順が無い・あるバッチの QC が 4 未満・QC が生体試料の注入を挟んでいないときは全体を行わず、理由を steps に書く（drift_mode="on" で条件を満たさなければ止める）。内部標準で換算済みのデータに QC があるときは既定を決めず needs_input で尋ねる。
  • 反復注入のまとめは個体 ID が頼り。同じ subject_id の注入だけを 1 試料にまとめる。無ければ各注入を 1 個体とみなし、その旨を結果に書く。反復らしい試料名は注意として知らせるだけで、自動ではまとめない。
  • 同定確度は報告するだけで仮定しない。MS/MS のフラグと実スペクトルを全経路で区別する。Level 1 は主張しない。スペクトル照合の順位付けは上流の順位付けのタプル全体を再現していない（library トピック）。
  • pipeline は上流だけ。Console を回して極性ごとの解析フォルダと受領を作るまでで、統計は計算しない（その先は load_dataset(pipeline_path=…, polarity=…) から）。Console の自動再試行はしない。旧 v1 の run は読むだけ。
  • Console は黙って同定 0 件になりうる。メソッドファイルを ASCII で読むので非 ASCII のパスは化け、脂質ライブラリが空でも完走する。サーバは実行の前にこれらをコード（METHOD_ENCODING_UNSUPPORTED LBM_NOT_FOUND ほか）で止める。
  • 解析の記録はデータの側に置く。目的・レポート・図・統計の記録は解析フォルダ配下の reports/ に書き、クローンの下には書かない。data/ は追跡外。
  • パスウェイの handoff は行を落とす。中間 mzTab-M に載るのは脂質として読める行だけで、名前・Ontology・組成式で経路（as_is / name / class_formula）に入らない行は理由つきで落とす。使った行と落とした行の数は戻り値の handoff で必ず確かめる。研究室サーバを設定していれば中間 mzTab-M はそのサーバへ送られる。
  • 再解析のツールは研究の結論を判定しない。dataset_analysis_run などは数字・向き・閾値の機械的な当てはめと rule_hash を返し、「再現した」「明らかに別物」は再解析の側の規則で決める。
  • 候補付けは脂質規則を見ない。curation_suggest の候補はスペクトル類似度と制約だけで並び、MS-DIAL の脂質クラス規則（診断イオン・鎖決定）を評価していないので、assign は既定で和組成として記録する。
  • キュレーションの会話内表示は未検証。Claude Desktop のローカル stdio サーバでは MCP Apps の _meta.ui が落ちる（anthropics/claude-ai-mcp#1069）。ブラウザで html_path を開き、ビューアの Submit で直接送る経路が主（受け口が無ければ送信用テキストを貼る）。
  • MS-DIAL は _tags.xml を丸ごと書き直す。アラインメントを保存するたびにメモリ上のタグで上書きし、読むのはプロジェクトを開くときだけ。ビューアの Submit・curation_submit の反映は、プロジェクトを閉じてから送り、開き直して確かめる。
  • MS-DIAL で絞り込まれたデータの likely_wrong。MS-DIAL は同定時に precursor の許容幅を課しているので、precursor_unmatched はまず立たない。強い理由の大半は class_rule_rejected と dmz_out。likely_wrong が少なくても「全部正しい」ではなく、suspect の理由コードを読む。
  • 定量は任意のプラグイン頼み。内部標準の正規化・極性の統合・付加体の選別の規則は外部パッケージにあり、[quant] rules を設定しないと定量の 4 ツールは使えない。内部標準の参照表は呼び出しごとに指定する。
  • Windows の venv。venv の Scripts\python.exe は中継ランチャなので、pipeline の worker と子プロセスは本体の解釈系を __PYVENV_LAUNCHER__ 付きで起動する（ランチャの pid を相手に生存確認・取消をしないため）。
